# TUI 聊天客户端

Status: ready-for-agent

## Problem Statement

这个仓库有一个能跑的服务端：HTTP 接口、SSE 推送、JWT 鉴权、SQLite + sled 双存储。但没有任何能日常使用的客户端——`assets/index.html` 只是占位，`api.http` 是过期的手工请求样例。想真正跟这个服务端聊天，只能在终端里手搓 curl，而且拿不到实时推送、看不到会话列表、也没有未读。

我要的是一个能在终端里打开就用的聊天客户端：登录、看到会话、点进去聊。

服务端这一侧还有个直接挡住客户端的问题：会话列表接口的排序是在**分页之后**才在内存里做的，SQL 本身没有 `ORDER BY`。所以每一页内部有序，页与页之间的顺序是任意的——客户端要么拉完所有页自己重排，要么接受"最近聊的人出现在列表中间"。

## Solution

在同一 workspace 里加一个新的 member crate，产出 `ratatui` 写的终端客户端：左侧会话列表（按最近消息倒序），右侧当前会话的消息流，底部单行输入。启动时登录或注册；消息通过 SSE 实时到达；断流自动重连并补拉。

同时修掉服务端会话列表的排序缺陷（`ORDER BY` + 放宽分页上限），让接口返回的顺序就是真实顺序，客户端不必拉全量。

## User Stories

### 认证与账号

1. 作为一个终端用户，我希望用用户名和密码登录，以便进入我的会话。
2. 作为一个新用户，我希望在客户端里直接注册账号，以便不依赖 curl 就能开始使用。
3. 作为一个输错密码的用户，我希望看到服务端返回的具体错误信息而不是笼统的"登录失败"，以便知道是名字错了还是密码错了。
4. 作为一个注重安全的用户，我希望密码只存在于内存、不写进任何配置文件，以便机器被别人拿到时不会连账号一起丢。
5. 作为一个长时间挂着客户端的人，我希望会话在第 50 分钟主动续登，以便聊天不被打断。
6. 作为一个续登失败的用户，我希望被带回登录页，以便知道需要重新输入凭据，而不是对着一堆 401 发懵。
7. 作为一个退出程序的用户，我希望本地令牌被清掉，以便下次启动是干净的登录页。
8. 作为一个要连远程服务端的人，我希望用 `--server` 指定地址，以便不必改代码重新编译。

### 会话列表

9. 作为一个登录成功的用户，我希望立刻看到会话列表，以便知道有哪些人在等我回话。
10. 作为一个用户，我期望列表按最近一条消息的时间倒序，以便最近聊的人在最上面。
11. 作为一个用户，我希望每个条目显示对方名字、最后一条消息摘要和时间，以便不点进去也能判断要不要回复。
12. 作为一个用户，我期望未读完的会话有明确的未读标记，以便一眼看到哪里欠回复。
13. 作为一个用户，当某个会话是"从来没读过"时，我希望看到一个区别于数字的标记，以便区分"1 条未读"和"全部未读"。
14. 作为一个会话很多的人，我希望滚动到底部时能加载下一页，以便不必重启就能看到更早的会话。
15. 作为一个用户，我希望当前打开的会话在列表里高亮，以便知道我正处在哪个会话里。

### 开始一个会话

16. 作为一个用户，我希望用 `/open <名字>` 打开一个从未聊过的好友，以便不必先等对方给我发消息才能开始对话。
17. 作为一个名字记不全的用户，我希望 `/open` 支持模糊匹配、多个结果时让我选，以便不必记住准确的用户名。
18. 作为一个名字打错的用户，我希望看到"找不到这个用户"的提示，以便知道是打错了而不是网络坏了。
19. 作为一个用户，我希望打开会话的那一刻就看到历史消息，以便接着之前的话题说。

### 收发消息

20. 作为一个用户，我希望在底部输入框打字并按 Enter 发送，以便快速回复。
21. 作为一个用户，我希望自己发的消息立刻出现在消息流里、不等服务端回显，以便输入感觉是即时的。
22. 作为一个用户，我希望自己的消息和对方的消息在视觉上可区分，以便一眼分清谁说的。
23. 作为一个发送失败的用户，我希望输入内容被保留、错误显示在状态行，以便不必重打一遍。
24. 作为一个用户，我希望每条消息带发送时间，以便感知对话的节奏。

### 实时

25. 作为一个用户，我希望对方发来的消息立刻出现，以便像真实聊天一样。
26. 作为一个正在看别的会话的用户，我希望收到新消息时对应条目未读 +1 并跳到顶部，以便不切过去也知道有新消息。
27. 作为一个用户，我希望心跳不会显示成消息，以便消息流里只有真正的内容。
28. 作为一个网络断过的用户，我希望客户端在持续 15 秒收不到任何字节后察觉并自动重连，以便不用手动重启。
29. 作为一个断线期间有人给我发消息的用户，我希望重连后那些消息被补回来且不重复，以便不漏消息也不看到重复。
30. 作为一个用户，我希望断线时状态行明确显示"连接断开，正在重连"，以便知道现在的沉默不是对方没理我。

### 已读

31. 作为一个打开会话的用户，我希望进去就算已读，以便列表里的未读标记消失。
32. 作为一个停留在会话里的用户，我希望收到新消息时也保持已读，以便不会出现"人就在会话里却显示未读 1"。

### 好友

33. 作为一个用户，我希望按用户名搜索并发起好友请求，以便建立联系。
34. 作为一个收到请求的用户，我希望看到待处理的请求并通过或拒绝，以便管理我的联系人。
35. 作为一个用户，我希望看到我的好友列表，以便知道可以跟谁聊。

### 健壮性

36. 作为一个把终端窗口缩小的用户，我希望布局优雅降级而不是崩溃，以便不丢当前状态。
37. 作为一个发长消息或用中文的用户，我希望换行正确，以便不看到被截断的内容。
38. 作为一个服务端不可达的用户，我希望看到明确的连接错误，以便分清是网络问题还是程序崩了。

## Implementation Decisions

### 服务端（前置改动）

- 会话列表查询加 `ORDER BY latest_mid DESC, id DESC`。`latest_mid` 是会话最近一条消息的 id，而消息 id 来自 sled 的单调递增序列，因此它就是"最近活跃"的精确代理，不需要新增时间列或迁移。`id` 作为并列时的稳定决胜条件。
- `PageReq.limit` 的上限从 10 提到 50。`PageReq` 目前只有会话列表一个消费者，改动不影响其他接口。
- `AppState` 目前把 SQLite 路径和 sled 路径硬编码在构造过程里。改成可从参数或环境变量注入，让测试能用临时目录启动整个路由器——这是服务端那半个改动唯一的可测性来源。

### 客户端

- 新 crate 作为 workspace member，产出单一二进制。**不依赖 `entity` 和 `msg`**：客户端只讲 HTTP 和 JSON，不应该把 sea-orm 和 sled 拖进构建图。栈是 `ratatui` + `crossterm` + `reqwest` + `tokio`。
- 五个模块：**会话模型**（领域类型 + 线缆翻译）、**API 客户端**、**会话状态机**（纯函数，无 I/O 无渲染）、**渲染**（状态 → 帧，纯）、**接线**（tokio 选主循环，把键盘、SSE、状态机串起来）。
- **线缆翻译只在一个地方发生。** SSE 推送的 `ChatMessage` 是三层外部标签嵌套（`payload.detail.Normal.content.content`），而历史接口返回的是扁平的 `msg: String`。同一个概念有两种线上形状；会话模型模块是唯一知道这件事的地方，对外只暴露一个 `Message` 类型。
- **鉴权**：普通请求走 `Authorization: Bearer`；SSE 必须走 `?token=` 查询参数，因为 `EventSource` 语义下加不了 header。第 50 分钟主动重新登录换取新令牌，密码只活在内存。不使用 `/token/renew`——它带 `FIXME` 且有 `check_login` 前置，救不回已经过期的令牌。
- **会话列表**：启动拉第一页（limit 50），滚动到底再拉下一页。每页到达后客户端仍按消息时间重排一次，作为对服务端顺序的防御。
- **列表刷新**：收到 `Chat` 事件后 debounce 1–2 秒重新拉列表。不在客户端本地重算"最后一条消息 + 未读数 + 排序"，因为那是服务端唯一权威的逻辑，重算一遍必然漂移。
- **重连**：存活信号是服务端每 5 秒一次的 keep-alive 注释行（由 SSE 响应包装层生成，与事件循环是否还活着无关），**不是** `Heartbeat` 事件——后者每 60 秒才发一次，拿它当心跳会每分钟误判一次断流。持续 15 秒（三个注释周期）收不到任何字节即判定断流。此外服务端在接收端落后时会主动结束响应，客户端会看到流正常关闭，同样按断流处理。重连后补拉当前会话的历史 → 按 `mid` 去重合并 → 重拉会话列表。`mid` 是全局唯一的，可以直接当去重键。
- **发送**：乐观追加一条 pending 消息，服务端返回的 `mid` 是 JSON 字符串（不是数字），用它把 pending 转成 confirmed。
- **开始会话**：`/open <名字>` 走 `GET /user/find/{name}` 做模糊匹配。不需要为了"播种"会话去调 `PUT /ri`——服务端的发送接口成功后会自己写已读位点，所以"打开空会话 → 发出第一条消息 → 会话自动出现在列表里"这条链本来就是通的。
- **已读**：打开会话时上报当前最大 `mid`；停留在会话中每收到一条新消息也上报一次。
- **错误呈现**：状态行，不弹窗。后端的错误 body 是裸 JSON 字符串，显示前要去掉外层引号。
- **输入**：单行，Enter 发送。`Esc` / `Ctrl-C` 退出。**偏差**：原计划的 `q` 退出已废弃——消息输入框占用了会话界面的所有可打印键，`q` 现在是普通消息字符；退出走 `Esc` / `Ctrl-C`（`/open` 选择器里 `Esc` 是取消，`Ctrl-C` 仍退出）。

## Testing Decisions

好的测试只断言穿过 seam 的可观察行为，不断言内部结构。喂进去什么、出来什么，中间怎么实现不关测试的事。

两个 seam：

- **会话状态机**（纯函数）。喂事件，断言状态：会话顺序、未读计数、当前会话切换、连接状态变化、重连补拉后的去重结果。因为没有任何 I/O，这类测试是同步的、毫秒级的、不需要端口也不需要临时目录。
- **HTTP 线缆**（wiremock 替身服务端）。断言两件事：请求形状（方法、路径、header、query 参数）和真实服务端 JSON 能被解析成领域类型。后者的样例直接从服务端的类型定义抄，不手写臆想的 JSON——这个仓库最容易被踩的就是那三层嵌套。

服务端那半个改动：集成测试，用临时目录 + 内存 SQLite 启动路由器，种三条乱序的已读位点，断言返回顺序正确。这依赖上面那条 `AppState` 可注入路径的改动。

**渲染不设 seam。** 布局靠跑起来看，不做快照测试。等渲染类 bug 真的开始反复出现，再补这一层。唯一的例外是一个不断言外观的冒烟测试：三个界面 × 一组尺寸（含 0×0、1×1、阈值边界）只要求不 panic——布局算术在小尺寸上 panic 是崩溃，不是观感问题。

**先例：几乎没有。** 这个仓库目前 7 个单元测试、0 个集成测试。本 spec 会建立第一个像样的测试先例，后续的 `/code-review` 会拿它当标准。

## Out of Scope

- **群聊**：第二阶段。会话模型预留群会话变体，但本 spec 不实现其行为。
- 消息撤回、编辑、删除（服务端的 `Replay` 变体从未被构造）
- 图片、文件、语音等非文本内容
- 位置与"附近的人"
- 管理端接口
- 多行输入
- 消息本地落盘缓存
- 会话内搜索
- 兼容修正前的服务端返回顺序（前后端同仓库，没有理由兼容一个刚被自己废弃的行为）

## Further Notes

- **SSE 会静默死亡。** 所有连接共享一个容量 128 的 broadcast channel，接收端一旦落后就 `break`——没有 error 事件。但它会让响应体正常结束，所以这种情况客户端能看到流关闭；真正的网络中断则不会有任何信号，只能靠 keep-alive 注释的缺席来发现。两种断法都要处理，重连逻辑是必需品，不是优化项。
- **时间是本地时间、无时区偏移**（`%Y-%m-%d %H:%M:%S`）。跨时区用户会看到错误时刻，但这是服务端的既成事实，客户端照单解析，不自行加偏移。
- **`api.http` 已过期**，别照抄：它假设响应外面包了一层 `data`，也用了不存在的路由。
- **已有行为不是 bug**：列表项里没有任何消息的会话会显示成"未知消息"+当前时间。当前选型不播种空会话，所以正常不会遇到。
- **服务端的一小时 session 缓存**意味着已建立的 SSE 连接不会在过期时被重新校验——连接还活着，但下一次普通请求会 401。客户端必须把这种情况当作"需要重新登录"而不是"服务端坏了"。
